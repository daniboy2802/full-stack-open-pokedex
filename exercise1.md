Imagina un equipo de seis personas a punto de publicar una aplicación escrita en Python. El riesgo no es solo que el código funcione en una máquina y falle en otra. Dos cambios pueden pisarse, alguien puede integrar sin correr las pruebas, o producción puede construirse con otras versiones de las librerías. Un pipeline de integración continua obliga a que el lint, las pruebas y el build ocurran siempre, en el mismo orden y sobre el mismo commit que se va a desplegar.

En el ecosistema de Python el estilo se revisa con Ruff o con Flake8, y el formato con Black o con el propio Ruff. Las pruebas unitarias se escriben con pytest. Si el proyecto usa anotaciones de tipos, mypy o pyright las comprueban antes de ejecutar la suite. Las dependencias se fijan con un lockfile de uv, Poetry o pip-tools, y el artefacto que llega a producción se empaqueta en una imagen de Docker para que el entorno de CI y el de producción coincidan.

Jenkins y GitHub Actions no son las únicas opciones. El mismo flujo se puede definir en GitLab CI, CircleCI, Buildkite, Azure Pipelines o Travis CI. Para un equipo pequeño, sin GPUs ni redes privadas, un servicio en la nube suele convenir más: no hay que administrar el servidor y se paga por minuto de ejecución. Un CI propio, como Jenkins, compensa cuando hace falta hardware especial, cuando los secretos no pueden salir de la red de la empresa, o cuando el volumen de builds hace más barato un servidor fijo.

Para elegir entre las dos haría falta saber cuántos builds se lanzan al día, cuánto dura cada uno, si las pruebas dependen de servicios internos y qué restricciones hay sobre las credenciales de producción.
